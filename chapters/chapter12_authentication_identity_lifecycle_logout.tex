\begin{enumerate}

\end{enumerate}

\section{MSISDN Normalization and Identity Provisioning}
In Bangladesh, mobile phone numbers (MSISDNs) are entered in various formats across mobile browsers, SMS links, and native webviews:
\begin{itemize}
    \item Full International Format: \texttt{+8801711000001}
    \item Country Code without Prefix: \texttt{8801711000001}
    \item Standard National Format: \texttt{01711000001}
    \item Local 10-digit Shorthand: \texttt{1711000001}
\end{itemize}

To prevent duplicate accounts and ensure deterministic user lookups, the authentication engine executes strict MSISDN sanitization before touching the database:

\begin{lstlisting}[language=python, caption={MSISDN Normalization Logic in Django / .NET 10}]
def normalize_msisdn(msisdn: str) -> str:
    # 1. Strip all non-digit characters (spaces, dashes, plus signs)
    cleaned = re.sub(r"\D", "", msisdn)
    
    # 2. Strip leading international country code (880)
    if cleaned.startswith("880"):
        cleaned = cleaned[3:]
        
    # 3. Strip leading national zero (0)
    if cleaned.startswith("0"):
        cleaned = cleaned[1:]
        
    return cleaned  # Returns canonical 10-digit string: e.g., '1711000001'
\end{lstlisting}

\subsection{Just-in-Time (JIT) Tenant Provisioning}
When a player logs in via \texttt{POST /api/login/}:
\begin{enumerate}
    \item \textbf{Global User Check (\texttt{auth\_user}):} The engine checks if the canonical username exists. If not, a new user entity is provisioned automatically with a secure default state.
    \item \textbf{Tenant Profile Check (\texttt{ParticipantDetail}):} Quizard checks for a tenant profile matching the player's \texttt{user\_id} and the incoming \texttt{portal\_id} (e.g., Portal 15 for bKash Web, Portal 16 for Banglalink, Portal 17 for Grameenphone, Portal 21 for Robi).
    \item \textbf{Referral \& Promo Attribution:} If a promotional campaign code (\texttt{promo=XYZ}) or referral token is present in the query parameters, it is linked to the participant's record to unlock promotional passes.
\end{enumerate}

\section{Two-Factor SMS OTP Verification Workflow}
For high-security portals or new mobile registrations requiring explicit carrier verification, Quizard integrates an automated SMS OTP gateway:

\begin{enumerate}
    \item \textbf{OTP Dispatch:} A cryptographically secure 6-digit random code is generated, stored in \texttt{ParticipantDetail.otp}, and dispatched via the Telecom SMS Gateway:
    $$\text{OTP} \in [100000, 999999]$$
    \item \textbf{Verification Request (\texttt{POST /api/otpverify\_api/}):} The client submits the MSISDN, OTP, and Company ID:
\begin{lstlisting}[language=json, caption={OTP Verification Request}]
{
  "msisdn": "01711000001",
  "otp": "482910",
  "company_id": 15
}
\end{lstlisting}
    \item \textbf{Validation and Account Activation:} The server compares the submitted OTP against the database record. Upon a match, \texttt{ParticipantDetail.is\_verified} is set to \texttt{true}, the temporary OTP is purged, and the authenticated session token is released.
\end{enumerate}

\section{Graceful Logout and Security Token Invalidation}
In multi-user environments (such as family members sharing a tablet or smartphone), incomplete logouts represent a critical security vulnerability where cached browser tokens could allow unauthorized tournament attempts or prize theft.

Quizard implements **Dual-Boundary Token Invalidation**:

\subsection{1. Server-Side Cryptographic Token Destruction}
When the player triggers sign-out, the client sends an authenticated request to \texttt{POST /api/logout/} carrying the active header:
$$\texttt{Authorization: Token 4f8a9b2c1d3e5f7a8b9c0d1e2f3a4b5c6d7e8f9a}$$

The server instantly executes:
\begin{lstlisting}[language={[Sharp]C}, caption={Server-Side Token Deletion in .NET 10 AuthService}]
public async Task LogoutAsync(string tokenKey, CancellationToken ct = default)
{
    // Instantly remove token from the database
    await _dbContext.AuthTokens
        .Where(t => t.Key == tokenKey)
        .ExecuteDeleteAsync(ct);

    _logger.LogInformation("Security token {TokenPrefix}... successfully invalidated.", 
        tokenKey[..6]);
}
\end{lstlisting}

Any subsequent attempt to reuse the old token immediately fails with an **HTTP 401 Unauthorized** error.

\subsection{2. Client-Side State and Storage Sanitization}
Upon receiving the HTTP 200 response from the logout endpoint, the Next.js frontend clears all client-side authentication artifacts:
\begin{itemize}
    \item Clears \texttt{localStorage.removeItem('token')} and \texttt{localStorage.removeItem('playerData')}.
    \item Resets the global React authentication state and Zustand stores to default unauthenticated values.
    \item Redirects the browser to the public splash/landing view, preventing backward navigation via browser cache.
\end{itemize}
